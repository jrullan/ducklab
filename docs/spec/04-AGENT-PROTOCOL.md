# 04 — Agent Protocol

`spec-1.2` — revised: two tools join the belt — `fs_write_lines` (§2.1), a
ranged write addressed by the line numbers `fs_read` shows, and `ask_advisor`
(§2.4), a mid-turn consult that never pauses; the `advisor` role gets a system
prompt and the implementer prompt gains the deliverables contract (§6). `spec-1.1`
made `ask_human` pause the run rather than block a terminal.

This document fixes how Ducklab talks to a model, what tools exist, how tool
calls are expressed for models that cannot do function calling, and what each
role must emit.

---

## 1. Message assembly

Every turn's message list is built in exactly this order. Nothing else is added.

| # | Role | Content |
|---|------|---------|
| 1 | `system` | Ducklab preamble (§1.1) + role prompt (§6) + gate description |
| 2 | `system` | Project memory: `.ducklab/docs/project.md` body, capped at 8 KB |
| 3 | `user` | Stage context: the artifacts relevant to this stage (§1.2) |
| 4 | `user` | The turn's rendered task prompt |
| 5 | `user` | Prior turns of this conversation, rendered per §1.3 |
| 6 | … | tool-call / tool-result pairs accumulated by the agent loop |

Rationale for keeping 2 and 3 as separate messages: prompt caching on API
providers keys on prefix stability, and 1–2 are stable across a whole project.

### 1.1 Ducklab preamble (verbatim, all roles)

```
You are a duckling in ducklab, a multi-model software development harness.

Ground rules, which you cannot change:
- ducklab, not you, runs git, runs the tests, and decides whether work passed.
  Do not attempt to commit, branch, merge, or push. Do not claim work is
  verified; you will be told the verification result.
- You act only through the tools you are given. If a tool you want is absent,
  say so plainly instead of pretending or improvising a shell workaround.
- Paths are relative to the project root. You cannot read or write outside it.
- If you are uncertain, say what you are uncertain about. A stated unknown is
  more useful here than a confident guess, because another model will read this.
- Be terse. Prose is not the deliverable.
```

### 1.2 Stage context

| Stage | Artifacts injected (read-only, as `user` message) |
|-------|---------------------------------------------------|
| intake | `project.md`; the `--from` seed document if given |
| spec | `requirements.md` (approved requirements only) |
| plan | `spec.md` + `requirements.md` titles |
| build | the task record; its spec section; the repo file tree (§1.4); prior failed attempts for this task (§1.5) |
| review | the diff, the gate result, the task record |
| operate | the bug record and any linked task |

### 1.3 Rendering prior turns

Prior turns appear as a single `user` message:

```
## Conversation so far

### Turn 1 — architect (A)
<content>


### Turn 2 — reviewer (B)
<content>
```

When `Turn.Anonymize` is true (I7), duckling ids are replaced by the stable
letters `A`, `B`, `C`, … assigned by first appearance, and any turn whose role
is the *author* of a candidate under review is omitted entirely.

### 1.4 Repo file tree

A depth-limited tree of tracked files, respecting `.gitignore`, capped at 400
entries. When it would exceed the cap, directories are summarised as
`src/ (37 files)`. Binary files are marked `[bin]`. This is generated by
`internal/vcs`, not by a shell tool.

### 1.5 Failed attempts memory

For a build turn on task `T`, Ducklab injects up to the 3 most recent failed
runs for `T` as:

```
## Approaches already tried and failed for this task
- r-2026…-k7q2 (pair): changed handler signature; gate failed: 2 tests red
  ("TestLogin/expired": nil pointer at auth.go:88)
```

This exists because a small model, re-run on the same task, reliably repeats the
same dead end. The summary line is generated deterministically from the run's
gate output — no extra model call.

## 2. The toolbelt

All tools live in `internal/tools`. Names are stable API; do not rename.

### 2.1 Filesystem (path-jailed, I4)

| Tool | Args | Notes |
|------|------|-------|
| `fs_list` | `{path?: string, depth?: int}` | Default `.`, depth 2. Respects `.gitignore`. |
| `fs_read` | `{path: string, start?: int, end?: int}` | 1-indexed inclusive lines. Returns content with line numbers prefixed as `NNNN\t`. |
| `fs_search` | `{pattern: string, glob?: string, max?: int}` | Go `regexp` syntax. Returns `path:line: text`, max 100. |
| `fs_write` | `{path: string, content: string}` | Creates parent dirs. Mutating. |
| `fs_write_lines` | `{path: string, start: int, end: int, first_line: string, content: string}` | Replaces lines `start..end` (1-based, inclusive — **the numbers `fs_read` shows**) of an existing file. `first_line` must equal the current content of line `start`; a mismatch refuses the write and **teaches the actual line**. Empty `content` deletes the range. The success message warns that numbers below the edit shifted. Mutating. |
| `fs_patch` | `{path: string, edits: [{search, replace}]}` | Each `search` must match **exactly once**; otherwise the whole call fails with a diagnostic naming the match count. Mutating. |
| `fs_delete` | `{path: string}` | Mutating. Refuses directories unless `recursive: true`. |

`fs_write`, `fs_write_lines` and `fs_patch` run the **write guard** (§3) before
touching disk.

The three exist because they fail differently. `fs_patch` re-types anchor
bytes and mismatches on files dense with quotes or backticks (28 straight
failures on one Go file); `fs_write` re-emits whole files, which a small seat
rightly fears. `fs_write_lines` re-types nothing but the new content: *what a
model never re-types, a model cannot mangle*. The fs_patch brake's remedy names
it first.

### 2.2 Execution

| Tool | Args | Notes |
|------|------|-------|
| `shell` | `{cmd: string, timeout_s?: int}` | Runs via `xplat.Shell` (`/bin/sh -c` on unix, `cmd /C` on Windows) with cwd = project root. Subject to policy §4. Mutating. |
| `verify_run` | `{}` | Runs the project's configured gate command and returns exit code + tail of output. Not mutating (by contract; a test suite that mutates the tree is the user's problem). |

### 2.3 Version control (read-only, I1)

| Tool | Args |
|------|------|
| `git_status` | `{}` |
| `git_diff` | `{ref?: string, path?: string}` |
| `git_log` | `{n?: int, path?: string}` |

There is deliberately no `git_commit`, `git_checkout`, `git_branch`,
`git_merge`, `git_push` or `git_worktree` tool. If a role's prompt implies one is
needed, the prompt is wrong.

### 2.4 Knowledge and coordination

| Tool | Args | Phase |
|------|------|-------|
| `artifact_read` | `{kind: "requirements"\|"spec"\|"plan"\|"project", id?: string}` | v0.3 |
| `task_read` | `{id: string}` | v0.3 |
| `bug_read` | `{id: string}` | v0.4 |
| `skill_list` | `{}` | v0.5 |
| `skill_read` | `{name: string}` | v0.5 |
| `skill_run` | `{name: string, args?: object}` | v0.5 |
| `mcp_call` | `{server: string, tool: string, args: object}` | v0.5 |
| `ask_human` | `{question: string, options?: [string]}` | v0.2 |
| `ask_advisor` | `{question: string}` | v0.6 |

`ask_advisor` is `ask_human` with no human: the implementer's door to the
advisor seat (05 §4.2, the rubber duck). It answers **inline, in the same turn,
and never pauses the run** — the advisor sees the question, the task and the
project documents, and replies as a senior colleague about the next move. With
no advisor seated the tool says so and points at the self-help path. Built for
the small seat that knows it is stuck but not what to do: one consult in place
of twenty more failed calls. Same seat, same cost accounting as a paused
question's advice.

`ask_human` **does not block a goroutine.** It checkpoints the run as `paused`
with a `pending_question`, emits a `human_needed` event, and yields control to
the engine supervisor (`01-ARCHITECTURE.md §7.1`). Any client may answer via
`POST /v1/runs/{id}/answer` (desktop: an inline input in the conversation lane;
CLI: `ducklab run answer`). The engine then resumes the run from the checkpoint
and delivers the answer as the tool result.

An unanswered question leaves the run paused **indefinitely, by design** — that
is a waiting state, not a hang. Two exceptions return the error result
`"no human available; proceed with your best judgement and state the assumption"`
instead of pausing: the run was started with `--yes`, or with autonomy `auto`
/`yolo`.

### 2.5 Toolbelt per role (default)

| Role | Tools |
|------|-------|
| `architect` | `fs_list`, `fs_read`, `fs_search`, `git_log`, `artifact_read`, `ask_human` |
| `implementer` | all fs (incl. `fs_write_lines`), `shell`, `verify_run`, `git_status`, `git_diff`, `artifact_read`, `task_read`, `skill_*`, `mcp_call`, `ask_human`, `ask_advisor` |
| `reviewer` | `fs_read`, `fs_search`, `git_diff`, `verify_run`, `artifact_read` — **read-only** |
| `judge` | `fs_read`, `git_diff` — read-only, and inputs are anonymised |
| `triager` | `fs_search`, `fs_read`, `bug_read`, `git_log` |
| `advisor` | `fs_read`, `fs_search`, `artifact_read` — read-only; grounds its advice, never does the work |
| `scribe` | `fs_read`, `artifact_read` |

A `Turn.Toolbelt` may only *narrow* this set, never widen it. Widening is a spec
violation and must be rejected at script-load time.

## 3. The write guard

Every mutating filesystem call passes these checks in order. Any failure returns
an error `Result` naming the rule, and emits a `policy_violation` event.

1. **Jail** — `filepath.EvalSymlinks` of the resolved absolute path must be
   inside the project root. (I4)
2. **Denylist** — refuse writes to `.git/`, `.ducklab/runs/`, `.ducklab/ducklab.db`,
   `.ducklab/lock`, and any path matching the user's `[git] protected_paths`.
3. **Marker guard** — refuse content containing conflict or protocol markers at
   line start: `<<<<<<<`, `>>>>>>>`, `=======` when the file is not already a
   conflicted file, and the literal strings ` ```ducklab ` or ` ```payload: `.
   A model leaking its own protocol into a source file is the single most common
   self-corruption; it must be impossible.
4. **Truncation guard** — for `fs_write` on an **existing** file, if the new
   content is under 40 % of the old size *and* the old file was over 200 bytes,
   the write is refused with:
   `"refused: this would shrink <path> from N to M bytes. If that is intended, use fs_patch, or write the file in full."`
5. **Binary guard** — refuse writing content with NUL bytes.
6. **Size guard** — refuse a single write over 1 MB.

Checks 3 and 4 may be disabled per run with `--unsafe-writes`, which is recorded
in the run manifest and printed in red. They are never disabled by default.

## 4. Shell policy

`shell` is the sharpest tool. Policy, in `internal/tools/policy.go`:

```toml
[shell]
mode = "guarded"        # off | guarded | free
deny = ["rm -rf /", "shutdown", "reboot", "mkfs", ":(){", "curl * | sh", "dd if="]
allow_prefixes = ["go ", "npm ", "pnpm ", "yarn ", "pytest", "python ", "cargo ",
                  "make ", "ls", "cat", "grep", "rg", "sed -n", "find", "git status",
                  "git diff", "git log", "node ", "tsc", "docker compose config"]
timeout_s = 120
network = "deny"        # deny | allow  (advisory: sets DUCKLAB_NO_NET=1, and on
                        # Linux may use unshare -n when available)
```

- `off` — the tool is not in any toolbelt.
- `guarded` (default) — a command must match an `allow_prefixes` entry and no
  `deny` entry. Otherwise the call returns an error result telling the model to
  ask the human, and under autonomy `manual`/`guarded` the human is offered a
  one-shot approval via `ask_human`.
- `free` — only the denylist applies.

Commands always run with cwd = project root, a scrubbed environment (the
process env minus every variable named in any provider's `api_key_env`, minus
`DUCKLAB_*` secrets), and a hard timeout. Output is captured combined
(stdout+stderr), capped, and returned with the exit code.

Windows: `xplat.Shell` uses `cmd /C`; `allow_prefixes` matching is
case-insensitive there.

## 5. Provider dialects and capability probing

### 5.1 Dialect selection

```
if duckling.Caps.NativeTools → Dialect A (native function calling)
else                         → Dialect B (fenced text protocol)
```

### 5.2 Probe procedure (`ducklab duckling probe`)

1. `GET {base_url}/models` — record availability; ignore failure.
2. Send a 1-token-ish request with a single trivial tool
   (`ducklab_probe(ok: boolean)`) and the instruction "call the tool with
   ok=true". If the response contains a well-formed tool call → `native_tools =
   true`.
3. Send a request with `response_format={"type":"json_object"}` asking for
   `{"ok":true}`. Parse → `json_mode`.
4. Context window: from `/models` metadata if present; else from a per-model
   table; else default 32768.
5. Write to `caps.json` with `probed_at`.

Probing costs money on API providers. It runs at most once per model per 30 days
and never during a `run`.

### 5.3 Dialect A — native function calling

Standard OpenAI `tools` / `tool_calls` for `kind = "openai"`; standard
`tools` / `tool_use` / `tool_result` blocks for `kind = "anthropic"`. Tool
schemas come from `Tool.Schema()`.

Handling of `finish_reason`:

| Value | Action |
|-------|--------|
| `tool_calls` / `tool_use` | execute and continue the loop |
| `stop` / `end_turn` | parse against the contract |
| `length` / `max_tokens` | **not** a valid answer. Retry once with a message instructing the model to be terse; then fail the turn with `ErrTruncated`. Never parse a truncated response. |
| `content_filter` | fail the turn with a clear message |

### 5.4 Dialect B — fenced text protocol

For local models that cannot emit function calls. The system prompt appends:

````
## How to use tools

When you want to use a tool, end your message with exactly one fenced block
tagged `ducklab` containing a single JSON object:

```ducklab
{"tool": "fs_read", "args": {"path": "src/main.go"}}
```

Rules:
- One tool call per message. Nothing after the closing fence.
- To pass a large or multi-line string (like file content), write the value as
  "@payload:N" and add a fenced block tagged `payload:N` after the ducklab block:

```ducklab
{"tool": "fs_write", "args": {"path": "src/main.go", "content": "@payload:1"}}
```
```payload:1
package main

func main() {}
```

- When you are finished and have no tool to call, reply with your answer and no
  `ducklab` block at all.
````

Parsing rules (normative):

1. Find all fenced blocks tagged exactly `ducklab`. If zero → this is a final
   answer; parse against the contract.
2. If more than one → error result: `"emit exactly one ducklab block"`, loop
   continues (counts as a turn).
3. Parse the block as JSON. On failure, and if repairs remain, resend with the
   JSON error text. Otherwise fail the turn (I6).
4. For every string value exactly matching `@payload:(\d+)`, substitute the
   verbatim body of the fenced block tagged `payload:<n>`. Missing payload →
   error result naming the missing id. The payload body is used **exactly**,
   minus one trailing newline added by the fence.
5. Unknown `tool` → error result listing available tool names.
6. Args failing the tool's JSON Schema → error result quoting the schema error.

Payload substitution is what makes weak models usable for file writes; JSON
string escaping of a whole source file is where they fail.

### 5.5 Thinking-token suppression

When `params.disable_thinking = true`, Ducklab must, in order of what the
provider supports:

1. send `{"chat_template_kwargs":{"enable_thinking":false}}` (vLLM/Qwen family),
2. send `{"reasoning":{"exclude":true}}` (OpenRouter),
3. append the stop sequences `["</think>"]` and strip any `<think>…</think>`
   span from the response content before parsing.

Step 3 always runs regardless, as a safety net. A response that is *only* a
thinking block is treated as empty and retried once.

## 6. Role prompts and output contracts

Prompts live in `internal/agent/prompts/<role>.md` and are embedded with
`//go:embed`. They are Go `text/template` with the variables listed per role.
A contract is a named parser in `internal/agent/contract`.

### 6.1 Contracts

| Contract | Expected output | Parser behaviour |
|----------|-----------------|------------------|
| `freeform` | anything | returns the text |
| `json:<name>` | one JSON object | strips fences, parses, validates against the named schema |
| `markdown_sections:<prefix>` | H2 sections whose text starts with `<prefix>-NNN` | returns the parsed sections; error if zero |
| `verdict` | JSON `{"verdict":"approve"\|"request-changes","findings":[…]}` | see §6.4 |
| `choice` | JSON `{"choice":"A"\|"B"\|…\|"none","reason":string}` | see §6.5 |
| `edits` | tool calls only; the final text is a summary | the diff is what matters; text is stored, not parsed |

When a contract is `json:*`, and the duckling has `json_mode`, Ducklab sets
`JSONMode = true`. Otherwise it relies on the parser's fence-stripping and the
repair loop.

### 6.2 `architect`

Variables: `.Stage`, `.Context`, `.Question`.
Contract: `markdown_sections:REQ` (intake), `markdown_sections:SPEC` (spec),
`markdown_sections:M` (plan).

```
You are the architect. You turn intent into a written artifact that another
model, with no memory of this conversation, can act on.

Rules:
- Every section starts with an H2 line: "## <ID> — <short title>".
- IDs are assigned by ducklab; reuse the IDs you are given and only allocate new
  ones from the next-free number you are told.
- Prefer fewer, sharper items over exhaustive lists.
- State what is OUT of scope as explicitly as what is in.
- Where you had to assume something, add "**Assumption:**" and say it.
- Never write implementation code in this artifact.
```

### 6.3 `implementer`

Variables: `.Task`, `.Spec`, `.Tree`, `.PriorFailures`, `.Gate`.
Contract: `edits`.

```
You are the implementer. You change the code so the task is done and the
verification command passes.

Method:
1. Read before you write. Use fs_read on every file you intend to change.
2. Make the smallest change that satisfies the task.
3. Use fs_patch for edits to existing files and fs_write only for new files or
   a full rewrite you can justify.
4. Run verify_run yourself before you finish. If it is red, keep working.
5. If the same tool keeps failing on you, or the gate stays red after several
   different attempts, call ask_advisor with what you tried and what you are
   stuck on. The advisor sees your situation and answers inline; the run does
   not pause. Consulting once beats twenty more failed calls.
6. When you finish, reply with a 3-line summary: what changed, why, and what you
   did not do.

Do not: reformat untouched code, rename things not named in the task, add
dependencies without saying so in your summary, or claim tests pass without
having run verify_run.
```


On a task run the implementer prompt is followed by the **deliverables
contract** (05 §4.2): the task's numbered bullets and the instruction to end the
reply with one JSON object reporting each by number —
`{"deliverables":[{"id":1,"status":"done"},{"id":4,"status":"blocked","note":"…"}]}`,
status ∈ `done | partial | not_done | blocked`.

### The advisor — the rubber duck

```
You are the advisor — the rubber duck. An implementer working alongside you is
allowed to bring you what it is stuck on: repeated tool failures, a gate that
stays red, a fight it cannot win. You listen to the whole story, then answer as
a senior colleague would: concretely, briefly, and about the NEXT move.

You are not the reviewer. You do not grade the work and you never see the diff
as a judge would; you see the implementer's reasoning and its trace, which the
reviewer must never read. Use that. Name the tool to use instead, the file to
read first, the assumption to drop. Cite the project's own documents when they
decide the matter.

You may read files (fs_read, fs_search, artifact_read) to ground your advice.
Do not attempt to do the work yourself. When a consult asks for a JSON answer,
reply with exactly that JSON object and nothing else.
```

The consult's contract (`json:advice`) is one object:
`{"action":"none"}` · `{"action":"note","note":"…"}` ·
`{"action":"stop","reason":"…","reshuffle":"…"}`. A malformed reply degrades to
`none` — advice is optional, the work is not.

### 6.4 `reviewer`

Variables: `.Diff`, `.Task`, `.GateResult`.
Contract: `verdict`.

```
You are the reviewer. You did not write this code and you are not here to be
agreeable. The tests have already been run; their result is given to you and is
not yours to dispute.

Judge only: correctness against the task, obvious defects, security, and whether
the change does something it was not asked to do. Style is not a finding unless
the project's conventions are written down and violated.

Reply with one JSON object:
{"verdict":"approve"|"request-changes",
 "findings":[{"severity":"critical"|"major"|"minor","file":"path","line":N,
              "issue":"one sentence","fix":"one sentence"}]}

If the gate result you were given is red, "approve" is not available to you.
An empty findings list with "approve" is a legitimate answer.
```

### 6.5 `judge`

Variables: `.Candidates` (anonymised A/B/…), `.GateResults`, `.Task`.
Contract: `choice`.

```
You are the judge. You are given several candidate solutions labelled A, B, …
and, for each, the result of running the project's verification command. You do
not know who wrote them and you must not ask.

Rules that bind you:
- A candidate whose gate is green beats any candidate whose gate is red,
  regardless of how the code reads.
- If exactly one candidate is green, choose it. Do not look for reasons to
  prefer a red one.
- If several are green, choose the one that changes least while satisfying the
  task.
- If all are red, answer "none" and say in one sentence what they all got wrong.
- You may not rewrite, improve, or merge candidates. Choose or refuse.

Reply with one JSON object: {"choice":"A"|"B"|…|"none","reason":"one sentence"}
```

### 6.6 `triager`

Variables: `.Bug`, `.OpenBugs`, `.Tree`.
Contract: `json:triage`.

```
You are the triager. Classify one bug report.

Reply with one JSON object:
{"severity":"critical"|"high"|"normal"|"low",
 "duplicate_of": "B-012" | null,
 "component": "short name or empty",
 "suspected_files": ["path", …],
 "reproducible": true|false|null,
 "task_title": "imperative one-liner for the fix task, or empty if not actionable",
 "reason": "one sentence"}

Base "duplicate_of" only on the open bugs you were given. If you are unsure,
answer null; a missed duplicate is cheaper than a wrongly closed bug.
```

### 6.7 `scribe`

Variables: `.Runs`, `.Range`, `.Kind`.
Contract: `freeform`.

```
You are the scribe. You write the release notes and changelog entries from the
list of accepted work you are given.

Write for the user of the software, not for the developer. One bullet per
user-visible change, in plain language, no ticket numbers in the text. Omit
internal refactors entirely unless they change behaviour. If the list contains
nothing user-visible, say exactly: "No user-visible changes."
```

## 7. Cost accounting

```
cost_usd = prompt_tokens/1e6 * cost.input_per_mtok
         + completion_tokens/1e6 * cost.output_per_mtok
```

If the provider returns cost directly (OpenRouter's `usage.cost`), that value
wins and is marked `cost_source: "provider"`. If a response carries no usage
data, Ducklab estimates tokens as `len(text)/4` and marks the record
`estimated: true`; estimated tokens are shown in reports with a `~` prefix and
never silently mixed with measured ones.

Budget enforcement is checked **before** each model call, using the spend so far
plus a worst-case estimate of the next call (`prompt_tokens_estimate * input +
max_tokens * output`). This prevents overshoot on the last call.
